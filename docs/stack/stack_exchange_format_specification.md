# Stack Exchange Format Specification

## Overview

This document specifies the stack data exchange format for the RinneGraph project. It is a common format used for import and export, designed to prioritize end-user convenience and provide developer-specific features as options.

## Design Principles

### 1. **End-User First**
- Directly usable CSV output from spreadsheet software (Excel, Google Sheets)
- Stack creation completed with minimal settings
- No enforcement of complex settings or naming conventions

### 2. **Pursuit of Simplicity**
- No file naming conventions required
- No forced directory structure
- Simplification of processing through automatic detection

### 3. **Implementation Independence**
- Hides RinneGraph implementation details
- Abstraction through intermediate data models
- Adaptable to future implementation changes

### 4. **Gradual Extension**
- Data Format: Pure data files (CSV, JSON)
- Manifest Format: Metadata control and multi-file management
- Guarantee of backward compatibility

## Terminology

- **Node**: A vertex in a graph (implements the Entity interface)
- **Link**: An edge between nodes (implements the Entity interface)
- **Stack**: A dataset composed of nodes and links
- **Entity**: A common base concept for nodes and links (internal implementation term)

## Supported Formats

### Data Format

#### 1. Single File Format

##### CSV Single File

**Example Node Data (without schema reference)**
```csv
id,name,age,department,status
person_001,Taro Yamada,35,Engineering,active
person_002,Hanako Sato,28,Marketing,active
```

**Example Node Data (with schema reference)**
```csv
id,labels,$name,$age,department
person_001,$Person,Taro Yamada,35,Engineering
person_002,$Person,Hanako Sato,28,Marketing
```

**Processing Rules:**
- `id` column: Required, custom ID for the node (user-defined identifier)
- `labels` column: Optional, multiple labels can be specified as comma-separated values. If referencing a schema, prepend with `$` (e.g., `$MyLabel`).
- Other columns: Automatically processed as node properties. If a header is prepended with `$` (e.g., `$name`), that column references a schema definition.
- Empty cells: Excluded from properties.

**Notes for End Users:**
Typically, label names or property names (CSV headers) do not start with a `$` character. However, if they are used, the schema definition feature might unintentionally activate. It is recommended to avoid names starting with `$` unless there is a specific intention.

**About ID System:**
RinneGraph manages two types of IDs:

1.  **System ID**: Internal ID in UUIDv7 format, automatically generated by the application.
2.  **Custom ID**: A user-definable identifier (e.g., `person_001`, `TokyoBranch`).

-   During import: The value in the CSV `id` column is saved as a custom ID.
-   During export: The custom ID is output in the `id` column.
-   Searchable by both IDs.
-   Cross-reference within the same file (source/target for links) uses custom IDs.

**Example Link Data**
```csv
source,target,type,weight,since
person_001,person_002,$REPORTS_TO,1.0,2023-01-01
person_002,person_003,$MANAGES,1.0,2023-06-01
```

**Processing Rules:**
- `source` column: Required, source node ID
- `target` column: Required, target node ID
- `type` column: Required, link type. If referencing a schema, prepend with `$` (e.g., `$MyType`).
- Other columns: Automatically processed as link properties

**Automatic Detection Logic**
```
Read CSV file
↓
Analyze header row
↓
if (id column exists) {
    Process as node data
} else if (source && target && type columns exist) {
    Process as link data
} else {
    Error: Unknown format
}
```

##### JSON Single File

**Node Data JSON**
```json
{
  "nodes": [
    {
      "id": "person_001",
      "labels": ["$Person", "$Employee"],
      "properties": {
        "$name": "Taro Yamada",
        "$age": 35,
        "department": "Engineering",
        "status": "active"
      }
    }
  ]
}
```

**Link Data JSON**
```json
{
  "links": [
    {
      "source": "person_001",
      "target": "person_002",
      "type": "$REPORTS_TO",
      "properties": {
        "weight": 1.0,
        "since": "2023-01-01"
      }
    }
  ]
}
```

**Mixed Data JSON**
```json
{
  "nodes": [
    {
      "id": "project_001",
      "labels": ["$Project"],
      "properties": {
        "$name": "AI Research",
        "status": "active",
        "budget": 500000
      }
    }
  ],
  "links": [
    {
      "source": "person_001",
      "target": "project_001",
      "type": "$LEADS",
      "properties": {
        "responsibility": "technical"
      }
    }
  ]
}
```

**Processing Rules:**
- `nodes`: Array of node data (optional)
- `links`: Array of link data (optional)
- Either `nodes` or `links` is required (can include both)
- A single file can contain both node and link data

### JSON Data File Processing Rules

1.  **Required fields**: `nodes` and/or `links`
2.  **Ignored fields**:
    - All top-level fields other than `nodes` and `links`
    - Example: `_metadata`, `version`, `schema`, `created_at`, etc.
3.  **Processed content**: Only the contents of the `nodes` and `links` arrays.

#### 2. Multiple File Support (Application Feature)

Multiple file processing is a feature provided by desktop applications and command-line tools. All file formats can be freely combined.

##### Basic Combination Examples

**Multiple CSV files**
```
Import target:
├── team_members.csv      # Node data
├── relationships.csv     # Link data
└── departments.csv       # Additional node data
```

**Mixed CSV + JSON**
```
Import target:
├── people.csv           # CSV node data
├── projects.json        # JSON data (mixed nodes and links)
└── collaborations.csv   # CSV link data
```

**Existing Stack + Additional Data**
```
Import target:
├── existing_project.stack/   # Existing stack
├── new_members.csv          # Additional node data
└── new_connections.csv      # Additional link data
```

##### Stream Processing Rules

**Node Processing Phase (Stage 1)**
- All node files are processed sequentially in a stream
- Each node is read, validated, and written to RinneGraph
- On ID duplication: Existing nodes are updated with later loaded data
- Property merging: New properties are added to existing properties
- Label merging: Existing and new labels are integrated
- Memory usage: Only one node's worth of data at a time

**Link Processing Phase (Stage 2)**
- All link files are processed sequentially in a stream
- Each link is read, referential integrity checked, and written to RinneGraph
- Referential integrity: References to non-existent node IDs are recorded in the error log
- Same (source, target, type) combination: Properties are merged
- New links: Added as is
- Memory usage: Only one link's worth of data at a time

**Validation / Error Handling**
- Validation performed before writing each record
- Processing continues even if an error occurs (the corresponding record is skipped)
- All errors are logged and a report is displayed at the end

**Metadata Generation**
- Metadata including statistical information is automatically generated after processing is complete
- Stack name: Inferred from the first file name
- Description: Includes list of processed files and statistical information

### Manifest Format

#### Manifest File (Metadata / Multiple File Management)

The Manifest Format is a file format automatically generated and referenced by the application. Developers can create it manually, but it is not intended for users to create manually.

**Usage Scenarios:**
- **During export**: Application automatically generates a manifest along with multiple file output
- **During import**: Application automatically references and integrates files if a manifest is found

If a manifest file exists, the `meta` directory is not required.

#### Basic Manifest File Example

```json
{
  "metadata": {
    "name": "Research Project Data",
    "description": "Dataset for university research project",
    "author": "Research Team",
    "version": "1.0.0",
    "tags": ["research", "university", "collaboration"],
    "thumbnail": "thumbnail.png"
  },
  "files": [
    "researchers.csv",
    "collaborations.csv",
    "projects.json"
  ]
}
```

#### Detailed Manifest File Example (including developer features)

```json
{
  "metadata": {
    "name": "Advanced Project Stack",
    "description": "Project stack with advanced settings",
    "author": "Developer Name",
    "version": "2.0.0",
    "tags": ["development", "advanced", "project"],
    "thumbnail": "stack_thumbnail.jpg",
    "created_at": "2024-01-01T00:00:00Z",
    "schema_version": "1.0",
    "export_info": {
      "exported_at": "2024-12-01T10:00:00Z",
      "app_version": "1.2.0",
      "node_count": 150,
      "link_count": 320
    },
    "validation": {
      "expected_node_count": 150,
      "expected_link_count": 320,
      "checksum": "sha256:abc123...",
      "data_integrity_check": true
    }
  },
  "schema": "schema.json",
  "files": [
    "team_members.csv",
    "project_relationships.csv",
    "additional_data.json",
    "dataset_core_team.json",
    "dataset_managers.json"
  ]
}
```

#### Manifest Format Behavior

**Automatic Generation During Export:**
1.  `manifest.json` is automatically created when multiple files are output.
2.  Stack metadata (name, description, author, etc.) is recorded.
3.  A list of output files and information about each file is recorded.
4.  (Optional) Schema information is output as `schema.json`, and the `schema` path is recorded in the manifest.

**Automatic Processing During Import:**
1.  Searches for `manifest.json` within the specified directory or directly specifies `manifest.json`.
2.  If found, integrates files based on the manifest.
3.  Applies metadata as stack information.
4.  **Schema Resolution:**
    - If a path is specified in the `schema` field of the manifest, that file is read as a schema.
    - If the `schema` field is not present, and `schema.json` exists in the same directory as the manifest file, it is automatically read.
    - If a schema is loaded, mapping of identifiers starting with `$` (labels, link types, etc.) in the data to display names is performed.
5.  If no manifest is found, files are processed individually.

**User Tasks:**
- Only prepare data files (CSV, JSON).
- No manual creation of manifest or schema files required (except for advanced use).

**Developer Tasks (Optional):**
- Manual creation and editing of manifest and schema files are possible for advanced control.
- Supports detailed metadata settings and management of complex file structures.
- Supports direct loading with the `--manifest` option in stack management tools.

**Application Implementation Notes:**
- The import file selection dialog should allow selection (opening) of directories containing `manifest.json`.
- When a directory is selected, the manifest file is automatically detected and file integration processing is performed.
- Supports both individual file selection and directory selection.

### Schema Definition File

The schema definition file is an optional JSON file for mapping identifiers (usually English) used in data files to display names and data constraints displayed in the application. This separates the structural meaning of the data from human-readable displays and validation rules.

#### Purpose
- **Ensure Data Quality**: Centrally manage validation rules such as type definitions, mandatory checks, and uniqueness constraints.
- **Readability and Maintainability**: Use consistent, programmatically manageable identifiers in data files, and manage display names and rules centrally in the schema file.
- **Flexible Data Definition**: Users can freely design internal identifiers that do not necessarily match display names.

#### File Name and Location
- **Default file name**: `schema.json`
- **Location**: Same directory as the manifest file, or the path specified in the `schema` field of the manifest.

#### Structure and Example

A schema file is a JSON object with three top-level keys: `labels`, `link_types`, and `properties`. The value for each identifier is an object containing detailed settings.

**Basic Structure:**
```json
{
  "labels": {
    "identifier": { "display_name": "display name", ... },
    ...
  },
  "link_types": {
    "identifier": { "display_name": "display name", ... },
    ...
  },
  "properties": {
    "identifier": { "display_name": "display name", ... },
    ...
  }
}
```

**Detailed Example (including future extensions):**
```json
{
  "labels": {
    "Person": {
      "display_name": "Person"
    },
    "Organization": {
      "display_name": "Organization"
    }
  },
  "link_types": {
    "BELONGED_TO": {
      "display_name": "Belongs To",
      // --- Future Extensions ---
      "allowed_connections": [
        { "from": "Person", "to": "Organization" }
      ]
    }
  },
  "properties": {
    "name": {
      "display_name": "Name",
      "type": "string", // Future extension: Data type
      "required": true   // Future extension: Required property
    },
    "employee_id": {
      "display_name": "Employee ID",
      "type": "string",
      "unique": true,    // Future extension: Uniqueness constraint
      "pattern": "^EMP[0-9]{5}$" // Future extension: Regular expression pattern
    },
    "status": {
      "display_name": "Status",
      "type": "string",
      "default": "active" // Future extension: Default value
    }
  }
}
```

#### Processing Rules

-   **Principle of Schema Reference**: When referencing a schema definition in a data file, prepend the identifier with a `$` prefix. Identifiers without `$` will be treated as string literals, even if defined in the schema, and will not be transformed.
-   **Scope of `$` Prefix Application**:
    -   **JSON**: Applied to each element in the `labels` array, each key in the `properties` object, and the `type` key in the `links` object.
    -   **CSV**: Applied to data values in `labels` and `type` columns, and property key names in the header row.
-   **Scope of Initial Implementation**: In the current version, only the `display_name` key within each schema definition object is interpreted. Other keys (e.g., `type`, `required`) are reserved for future extensions and are ignored in the current version.
-   **If Schema File Does Not Exist**: Identifiers with a `$` prefix will be treated as the string with `$` removed (e.g., `"$Person"` -> `"Person"`).

### Dataset Files

There are two types of datasets. Each dataset is represented as one JSON file.

#### 1. Static Dataset

A dataset that explicitly collects individual entities. Filters cannot be applied.

```json
{
  "dataset": {
    "name": "selected_members",
    "description": "Selected members",
    "type": "static",
    "created_at": "2024-01-01T00:00:00Z",
    "source": "manual_selection",
    "references": [
      "team_members.csv",
      "departments.json"
    ]
  },
  "nodes": [...],  // Explicitly selected nodes
  "links": [...]   // Explicitly selected links
}
```

#### 2. Smart Dataset

A dataset that dynamically filters data based on filter conditions. Individual data cannot be added.

```json
{
  "dataset": {
    "name": "core_team",
    "description": "Core team members",
    "type": "smart",
    "filter": {
      "node_labels": ["Person"],
      "properties": {
        "status": "active",
        "role": "core"
      }
    },
    "created_at": "2024-01-01T00:00:00Z",
    "source": "team_data",
    "references": [
      "team_members.csv",
      "departments.json"
    ]
  }
  // nodes, links are not included (dynamically generated by filter)
}
```

#### Dataset Determination Rules

-   `dataset` key exists → Dataset file
-   `dataset` key does not exist → Normal data file
-   `dataset.type` is `"static"` → Static dataset (includes nodes/links)
-   `dataset.type` is `"smart"` → Smart dataset (does not include nodes/links)

#### External File References

-   `references` array can specify external files to reference
-   Reference file existence check performed during import
-   Referenced files are automatically included in the import target

### Binary File Support

#### Overview

The stack exchange format allows associating binary files such as images, documents, audio, and video as node properties. Binary files are managed separately, and node data refers to their paths or identifiers.

#### Handling Binary Files

##### 1. File Reference Type Properties

When a node property refers to a binary file, the following format is used:

**File Reference in CSV**
```csv
id,name,profile_image:files,documents:files
person_001,Taro Yamada,images/yamada.jpg,"docs/resume.pdf,docs/portfolio.pdf"
person_002,Hanako Sato,images/sato.png,docs/report.pdf
```

**File Reference in JSON**
```json
{
  "nodes": [
    {
      "id": "person_001",
      "labels": ["Person"],
      "properties": {
        "name": "Taro Yamada",
        "profile_image": {
          "type": "files",
          "paths": ["images/yamada.jpg"],
          "mime_type": "image/jpeg",
          "size": 102400
        },
        "documents": {
          "type": "files",
          "paths": [
            "docs/resume.pdf",
            "docs/portfolio.pdf"
          ]
        }
      }
    }
  ]
}
```

##### 2. Directory Structure

Recommended directory structure for a stack containing binary files:

```
my_stack/
├── manifest.json
├── nodes.csv
├── links.csv
├── images/              # Image files
│   ├── yamada.jpg
│   └── sato.png
├── documents/           # Document files
│   ├── resume.pdf
│   └── report.pdf
└── assets/              # Other assets
    └── audio/
        └── interview.mp3
```

##### 3. Binary File Management in Manifest

Binary files can be explicitly managed in the manifest file:

```json
{
  "metadata": {
    "name": "Team Data with Assets",
    "version": "1.0.0"
  },
  "files": [
    "nodes.csv",
    "links.csv"
  ],
  "assets": {
    "base_path": ".",
    "files": [
      {
        "path": "images/yamada.jpg",
        "mime_type": "image/jpeg",
        "size": 102400,
        "checksum": "md5:1234567890abcdef"
      },
      {
        "path": "documents/resume.pdf",
        "mime_type": "application/pdf",
        "size": 204800,
        "checksum": "md5:fedcba0987654321"
      }
    ]
  }
}
```

#### File Reference Resolution

##### Relative Path Resolution Rules

1.  **Reference from CSV file**: Relative path based on the CSV file's location.
2.  **Reference from JSON file**: Relative path based on the JSON file's location.
3.  **Manifest `base_path`**: If specified, relative to that path.

##### File Validation

File validation during import:
- Check for file existence
- Validate MIME type (if specified)
- Check file size (if restricted)
- Validate checksum (if specified)

#### Security Considerations

##### 1. File Type Restrictions

Allowed file types can be restricted:

```json
{
  "import_settings": {
    "allowed_mime_types": [
      "image/jpeg",
      "image/png",
      "image/gif",
      "application/pdf",
      "application/msword",
      "audio/mpeg",
      "video/mp4"
    ],
    "max_file_size": 10485760  // 10MB
  }
}
```

##### 2. Path Traversal Countermeasures

- Relative paths are validated, and references to parent directories (`../`) are restricted.
- Absolute paths are rejected.
- Symbolic link following is restricted.

#### Export Behavior

##### 1. Export Including Binary Files

```bash
# Application operation
Export Stack > Include binary files > Select destination
```

Result:
```
exported_stack/
├── manifest.json
├── nodes.csv
├── links.csv
└── assets/          # Binary files are copied
    ├── images/
    └── documents/
```

##### 2. Export Excluding Binary Files

Only data is exported, file references are retained, but the actual files are not copied.

#### Import Behavior

##### 1. Binary File Processing Options

-   **Copy**: Copies binary files to the stack directory.
-   **Link**: Retains reference to original location (only within the same system).
-   **Ignore**: Processes file references as empty.

##### 2. Handling Missing Files

```json
{
  "import_options": {
    "missing_files": "warn",  // "error", "warn", "ignore"
    "create_placeholders": true
  }
}
```

#### File Type Specific Processing

##### Image Files
- Thumbnail generation (optional)
- EXIF information extraction and storage
- Format conversion (optional)

##### Document Files
- Text extraction (for search)
- Metadata extraction

##### Audio/Video Files
- Metadata extraction
- Duration, codec information storage

#### Storage Optimization

##### 1. Deduplication

Identical binary files are saved only once and referenced by multiple nodes:

```json
{
  "storage_optimization": {
    "deduplication": true,
    "method": "content_hash"
  }
}
```

##### 2. Compression

Large files can be compressed and saved:

```json
{
  "storage_optimization": {
    "compression": {
      "enabled": true,
      "threshold": 1048576,  // Files larger than 1MB
      "algorithm": "gzip"
    }
  }
}
```

#### Error Handling

| Error Type | Handling | Example |
|---|---|---|
| File not found | WARNING/ERROR | Referenced file does not exist |
| File size exceeded | ERROR | Exceeded configured maximum size |
| Invalid MIME type | ERROR | Unauthorized file type |
| No read permission | ERROR | No access permission to file |

### Stack Thumbnail Specification

#### Overview

This section specifies thumbnail images for visually representing the entire stack. Thumbnails are treated as part of the stack's metadata and are defined within `manifest.json`.

#### 1. Definition in Manifest

Add a `thumbnail` property to the `metadata` object in `manifest.json` to specify the path to the thumbnail image.

```json
{
  "metadata": {
    "name": "My Awesome Stack",
    "description": "This is a sample stack.",
    "thumbnail": "thumbnail.png"
  },
  ...
}
```

#### 2. File Specifications

- **File Format**: `PNG` or `JPEG` is recommended.
- **Recommended Size**: 1280px x 720px (aspect ratio 16:9) or larger is recommended.
- **Recommended Aspect Ratio**: **`16:9`** is strongly recommended. Creating images with this ratio makes them display as intended in various viewing areas.
- **Display Rules**: The application displays the provided image **trimmed to fit the display area while maintaining its center** (equivalent to CSS `object-fit: cover`). For example, when displayed in a square grid, the left and right sides of a `16:9` image will be cropped evenly.
- **Design Guidelines**: To ensure important information is not lost in any display area, it is strongly recommended to **place logos and main subjects within a `1:1` aspect ratio "safe area" at the center of the image**.
- **File Name**: Arbitrary, but a clear name like `thumbnail.png` or `cover.jpg` is recommended.
- **Local Files Only**: Supports only local files within the stack. Network URLs cannot be used.

#### 3. Path Resolution

- Thumbnail images are placed in the stack's `meta/` directory.
- The `metadata.thumbnail` property in `manifest.json` specifies only the file name (without path).
- During import, the application searches for the specified file name in the `meta/` directory.

#### 4. Import Behavior

- The application reads the `metadata.thumbnail` property and searches for the specified file name in the stack's `meta/` directory.
- If the specified file does not exist in the `meta/` directory, the application outputs a warning to the log and proceeds without a thumbnail.
- If no thumbnail is set, the application displays a default icon or an automatically generated preview.

#### 5. Export Behavior

- If a thumbnail is set for the stack, the image file is included in the `meta/` directory of the exported package.
- The file name is recorded in the `metadata.thumbnail` property of `manifest.json`.
- If no thumbnail is set, the `thumbnail` property is not included in `manifest.json`.

#### 6. Automatic Generation (Future Extension)

- If the user does not specify a thumbnail, the application could automatically generate a preview from the stack's graph structure and use it as a thumbnail.

## Data Type Specification

### Node Data Structure

```json
{
  "id": "string",                    // Required: Custom ID (user-defined unique identifier)
  "labels": ["string", "string"],    // Optional: Array of classification labels
  "properties": {                    // Optional: Attribute object
    "property_name": "value",        // Any property
    "numeric_value": 123,            // Numeric value
    "boolean_flag": true,            // Boolean value
    "array_data": ["item1", "item2"] // Array
  }
}
```

### Link Data Structure

```json
{
  "source": "string",               // Required: Custom ID of source node
  "target": "string",               // Required: Custom ID of target node
  "type": "string",                 // Required: Link type
  "properties": {                   // Optional: Attribute object
    "property_name": "value",       // Any property
    "numeric_value": 123,           // Numeric value
    "boolean_flag": true,           // Boolean value
    "array_data": ["item1", "item2"], // Array
    "weight": 1.0,                  // Example: Weight
    "created_at": "2023-01-01"      // Example: Creation date
  }
}
```

### Handling Data Types

#### Basic Principles
- All data is treated as strings by default
- Type conversion is performed only when explicitly specified
- If type conversion fails, the original string value is retained

#### Type Specification Method (Optional)

1.  **Type Specification in CSV Header**
    ```csv
    id,name,age:integer,active:boolean,joined_date:date,tags:list,photo:files
    person_001,Taro Yamada,35,true,2023-01-01,"tag1,tag2",profile.jpg
    person_002,Hanako Sato,twenty-eight,yes,2023/06/01,"tag3,tag4","avatar.png,badge.png"
    ```
    - Type name specified after a colon (:)
    - If no type is specified, treated as a string
    - If type conversion fails (e.g., "twenty-eight" in age column), retained as a string

2.  **Type Specification in JSON**
    - Value types are automatically determined in JSON
    - Explicit type specification is not required

#### Supported Data Types

The exchange format uses simplified types, which are mapped to the internal detailed type system during import.

| Exchange Format Type | Description | CSV Example (with type) | JSON Example | Mapping to Internal Type |
|---|---|---|---|---|
| `string` | String (default) | `"Taro Yamada"` | `"Taro Yamada"` | TextPropertyType |
| `integer` | Integer | `35` | `35` | IntegerPropertyType |
| `decimal` | Decimal | `123.45` | `123.45` | DecimalPropertyType |
| `boolean` | Boolean | `true` | `true` | BooleanPropertyType |
| `datetime` | Datetime | `2023-01-01T00:00:00Z` | `"2023-01-01T00:00:00Z"` | DateTimePropertyType |
| `date` | Date | `2023-01-01` | `"2023-01-01"` | DatePropertyType |
| `time` | Time | `14:30:00` | `"14:30:00"` | TimePropertyType |
| `url` | URL | `https://example.com` | `"https://example.com"` | UrlPropertyType |
| `email` | Email address | `user@example.com` | `"user@example.com"` | EmailPropertyType |
| `list` | List | `"tag1,tag2"` | `["tag1", "tag2"]` | ListPropertyType |
| `files` | File reference (single/multiple) | `images/photo.jpg` or `"doc1.pdf,doc2.pdf"` | `{"type": "files", "paths": ["images/photo.jpg"]}` | FileListPropertyType |
| `null` | Null value | Empty cell | `null` | - |

**Note:**
- Only simplified types are supported in the exchange format.
- Special types such as phone numbers, location information, colors, and binaries are treated as strings and converted on the application side.
- The `number` type has been abolished and separated into `integer` and `decimal`.

#### Type Conversion Rules

**Integer Type**
- Integer values only: `123`, `-456`
- If includes decimal point: conversion fails
- On conversion failure: retained as string, WARNING logged

**Decimal Type**
- Integer or decimal (floating-point number): `123`, `123.45`, `-0.001`
- Exponential notation also possible: `1.23e-4`
- Internally treated as Dart's double type
- On conversion failure: retained as string, WARNING logged

**Boolean Type**
- True values: `true`, `TRUE`, `1`, `yes`, `YES`
- False values: `false`, `FALSE`, `0`, `no`, `NO`
- Others: retained as string, WARNING logged

**Datetime Type**
- ISO 8601 format: `2024-01-01T00:00:00Z`, `2024-01-01T09:00:00+09:00`
- On conversion failure: retained as string, WARNING logged

**Date Type**
- ISO 8601 date format: `2024-01-01`
- Other common formats also possible (implementation dependent): `2024/01/01`, `01-01-2024`
- On conversion failure: retained as string, WARNING logged

**Time Type**
- ISO 8601 time format: `14:30:00`, `14:30:00.123`
- On conversion failure: retained as string, WARNING logged

**URL Type**
- Valid URL format: `https://example.com`, `http://localhost:3000`
- On conversion failure: retained as string, WARNING logged

**Email Type**
- Valid email address format: `user@example.com`
- On conversion failure: retained as string, WARNING logged

**List Type**
- Comma-separated: `tag1,tag2,tag3`
- Commas within elements escaped with double quotes: `"tag1,""tag,2"",tag3"`
- Empty list: empty cell
- Represented directly as an array in JSON

## Validation Rules

**Control of Validation Behavior:**
Validation options are specified during import execution.
- **Desktop app**: Select validation level in import dialog
- **CLI tool**: Control with flags such as `--strict`, `--skip-validation`

### 0. Data Integrity Validation (New Feature)

#### Manifest-Based Validation

If the manifest file includes a `validation` section, the following validations are performed:

```json
{
  "metadata": {
    "name": "Team Sample Stack",
    "validation": {
      "expected_node_count": 10,
      "expected_link_count": 5,
      "checksum": "sha256:abc123def456...",
      "data_integrity_check": true,
      "strict_mode": false
    }
  }
}
```

**Validation Items:**
- **Node count validation**: Checks if the number of nodes after import matches `expected_node_count`.
- **Link count validation**: Checks if the number of links after import matches `expected_link_count`.
- **Checksum validation**: Checks if the hash value of the data file matches `checksum` (optional).
- **Data integrity check**: Detailed validation of the integrity of all data (optional).

**Validation Level:**
- **strict_mode: true**: Aborts import on validation failure.
- **strict_mode: false**: Displays a warning and continues on validation failure (default).

**Validation Result Report:**
```
[INFO] Data integrity validation started
[SUCCESS] Node count validation: Expected 10, Actual 10 ✓
[SUCCESS] Link count validation: Expected 5, Actual 5 ✓
[WARNING] Checksum validation: Skipped (checksum not specified)
[INFO] Data integrity validation complete: All validation items succeeded
```

#### Automatic Validation Value Generation

Automatically generates validation values upon export:
- **Node count / Link count**: Automatically calculated from actual data.
- **Checksum**: Automatically generates SHA256 hash of data files.
- **Manifest update**: Automatically adds `validation` section.

### 1. Mandatory Field Validation

#### Node Data
- Check for existence of `id` field.
- Check for uniqueness of `id` values.
- Detection of empty `id` values.

#### Link Data
- Check for existence of `source`, `target`, `type` fields.
- Check for existence of referenced nodes.
- Detection of circular references.

### 2. Data Type Validation

- Type checking for numeric fields.
- Format verification for date fields.
- Structure verification for array data.

### 3. Integrity Validation

- Referential integrity of links.
- Duplicate node ID checks.
- Check for existence of mandatory properties.

## Error Handling

### Error Level Classification

| Level | Handling | Example |
|---|---|---|
| `FATAL` | Process aborted (cannot be skipped) | File unreadable, insufficient memory |
| `ERROR` | Corresponding data skipped | Missing mandatory field |
| `WARNING` | Data conversion continues | Type conversion failed |
| `INFO` | Information notification | Data conversion executed |

**Note**: If a `FATAL` level error occurs, the entire process stops. This level of error cannot be skipped. The handling of processed data is implementation-dependent.

### Example Error Message

```
[ERROR] Line 3: Node ID 'person_001' is duplicated
[WARNING] Line 5: Value 'thirty' in 'age' field cannot be converted to number. Processed as string
[INFO] Imported total 150 nodes and 45 links
```

### Handling Type Conversion Errors

The method for handling type conversion errors is implementation-dependent, but one example is to save entities where type conversion failed as a separate dataset, allowing them to be reviewed and corrected later.

## Character Encoding

### Basic Specification
- **Standard encoding**: UTF-8 (without BOM)
- **BOM support**: UTF-8 BOM is automatically ignored
- **Newline codes**: Supports LF (`
`), CRLF (`
`), CR (`
`)

### Other Encodings
The following encodings may be supported depending on implementation:
- UTF-8 with BOM
- UTF-16 (LE/BE)
- Shift-JIS
- EUC-JP
- Other locale-specific encodings

### Encoding Detection
1. Automatic detection by BOM
2. Inference from file content (implementation-dependent)
3. Explicit specification by user

### Error Handling
- Invalid characters: Replaced with replacement character (U+FFFD)
- Encoding detection failure: FATAL error

## Backward Compatibility

### Versioning
- Format version: Semantic versioning (e.g., 1.0.0)
- Recorded in `schema_version` field in manifest file

### Compatibility Guarantee
1.  **Major Version (1.x.x)**
    - Includes breaking changes
    - Not compatible with older versions

2.  **Minor Version (x.1.x)**
    - Addition of new features
    - Guarantees backward compatibility (can read older versions of files)

3.  **Patch Version (x.x.1)**
    - Bug fixes only
    - Full forward and backward compatibility

### Compatibility Strategy
- **Unknown fields**: Ignored and processing continues.
- **New types**: Processed as strings.
- **Deprecated features**: A warning is output, and conversion is attempted if possible.

### Migration Between Versions
```json
{
  "metadata": {
    "schema_version": "1.0.0",
    "minimum_reader_version": "0.9.0"
  }
}
```
- `schema_version`: Format version of this file
- `minimum_reader_version`: Minimum version required for reading
