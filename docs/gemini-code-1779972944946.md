# 無限スクロール・キャンバス実装における設計意思決定プロセス（Architecture Decision Log）

本作図ツールのコアとなる「無限スクロール（無限キャンバス）」の実装方針について、検討された要件、議論、および最終的な設計判断の推論プロセスを記録する。

---

## 1. 解決すべき主要要件と技術的課題

1.  **無限の作業空間:** ユーザーが全方位（負の座標を含む）に制限なくパン（スクロール）およびズームできること。
2.  **用紙エリアの存在:** OmniGraffleのように、無限空間の中に印刷・出力の基準となる固定の「用紙（アートボード）」が存在すること。
3.  **UI/UXの操作性:** マウスカーソルが指す位置を基準とした直感的なズーム、およびオブジェクトや用紙へのスナップ機能が実現できること。
4.  **パフォーマンス:** デスクトップ環境において、多数のオブジェクトや接続線を配置しても、パン・ズームが60fps/120fpsで滑らかに動作すること。

---

## 2. 思考過程と設計の変遷（議論の要約）

### 【議論 1】 キャンバスを「拡張」するか、空間を「固定」するか
* **初期案:** ユーザーが現在の画面外へパンした際、キャンバスコンポーネントのサイズ（縦横ピクセル）を動的に広げていく（拡張する）手法。
* **棄却理由:**
    * FlutterにおいてWidgetのサイズを頻繁に変更すると、レイアウトツリーの再計算（Layout Phase）が走り、パフォーマンスが著しく低下する。
    * 原点 `(0, 0)` より左上（負の領域）にオブジェクトを配置した際、全体の基準点をずらす必要があり、データモデルと表示ロジックの整合性を保つのが極めて困難になる。
* **決定方針:** キャンバスのサイズという概念を捨て、空間は最初から「型（double）の限界まで無限に広がっている」ものとして扱う。画面サイズ固定の「のぞき窓（ビューポート）」を最前面に置き、内部の変換行列（アフィン変換）だけでパンとズームを表現する。

### 【議論 2】 座標系の分離と負数座標の許容
* **思考プロセス:** 画面の物理的な位置（スクリーン座標）と、データが保持する位置（キャンバス座標）を完全に分離する必要がある。
* **結論:** 画面のルール（下方向が $Y$ のプラス）に従いつつ、原点より左上は `x: -500, y: -300` のような**負数（マイナス）の絶対座標**のままデータモデルに保存する。描画時およびクリック判定時に、以下の行列変換式を用いて相互変換を行う。
    * $X_{screen} = (X_{canvas} \times scale) + offset.dx$
    * $X_{canvas} = \frac{X_{screen} - offset.dx}{scale}$

### 【議論 3】 用紙エリア（アートボード）をどう定義するか
* **検討案:** 用紙を「背景にある巨大な1つのオブジェクト」として、他の図形と同じ配列で管理する手法。
* **棄却理由:** ユーザーの全選択（ボックス選択）で用紙まで動いてしまう、用紙エッジへのスナップ判定が複雑になる、画像出力時の切り抜き範囲として扱いづらい、といったデメリットが生じる。
* **決定方針:** 用紙はオブジェクトとは完全に切り離された**「メタ情報（環境設定）」**として定義する。データ構造を分離し、レンダリング時に「背景」→「用紙」→「オブジェクト群」の順で下から上に重ねて描画する。

### 【議論 4】 技術選定：Flutter Flame（ゲームエンジン）の是非
* **検討理由:** 無限スクロールやコンポーネント管理、カメラ制御が標準搭載されているため、高速化に寄与するのではないか。
* **棄却理由:**
    * **速度は変わらない:** Flameも最終的にはFlutterと同じグラフィックスエンジン（Impeller/Skia）の `Canvas` を叩いているため、純粋な描画速度の優位性はない。ツール系アプリでは、動かないときは描画をスキップできる `CustomPaint` の方がむしろ省電力である。
    * **Widgetとの親和性低下:** ドローツールでは、図形内でのインラインテキスト編集（TextField）や、OSネイティブの右クリックメニュー、インスペクタパネルの配置が必須となる。Flameのコンポーネント構造の中では、これら通常のFlutter Widgetを融合させる難易度が上がる。
* **決定方針:** 標準の `GestureDetector` + `CustomPaint` を採用し、テキスト編集時のみ `Stack` を使って通常の `TextField` を適切なスクリーン座標に動的にオーバーレイする構造とする。

---

## 3. 最終的なアーキテクチャ骨子

### コンポーネント構造

[Stack] (画面全体)
├── [GestureDetector] (パン・ズーム・クリック等のイベントをスクリーン座標で検知)
│     └── [CustomPaint] (Size.infinite で画面に固定。レイアウト負荷ゼロ)
│           └── [CustomPainter] (★ 内部でsave/translate/scaleを適用し、レイヤー順に一括描画)
├── [Positioned] (テキスト編集時のみ出現する、通常のFlutter TextField)
└── [Align / Positioned] (画面に固定されたツールバーやプロパティインスペクタ)


### 実装時の重要ロジック要件
1.  **ポインタ位置基準のズーム:** 拡大縮小時、マウスカーソルが指しているキャンバス上の座標が固定されるよう、ズーム後に `offset` を次の式で逆算・更新する。
    `offset.dx = X_{screen} - (X_{canvas} * scale_{new})`
2.  **ビューポート・カリング:** 大量オブジェクト配置時の軽量化のため、現在のスクリーン領域（四角形）をキャンバス座標に逆変換し、領域外にあるオブジェクトの描画（`object.draw`）をスキップする検知ロジックを挟む。

# 無限スクロール（無限キャンバス）ドローイングエリア 実装設計書

OmniGraffleやペイントツールのような、無限スクロールおよびズーム機能を備えたデスクトップ・ファーストのドローイングエリアをFlutterで実装するための設計骨子。

## 1. 座標体系の定義
システム内に以下の3つの独立した座標系を定義し、相互に変換する。

* **スクリーン座標系（Screen / View Coordinates）**
    * **基準:** 画面（ビューポート）の左上を `(0, 0)` とする物理的なピクセル座標。
    * **用途:** マウスイベント（クリック、ドラッグ、ホバー）の検知。
* **キャンバス座標系（Canvas / World / Scene Coordinates）**
    * **基準:** 仮想空間上の不変の基準点を `(0, 0)` とする絶対座標。
    * **用途:** 描画オブジェクト（データモデル）の座標保持、衝突判定。
    * **特徴:** 負数（マイナス）の座標も許容する（原点より左上への配置に対応）。$Y$ 軸は下方向を正（プラス）とする。
* **ローカル座標系（Local / Object Coordinates）**
    * **基準:** 各オブジェクトの中心または左上を `(0, 0)` とする相対座標。
    * **用途:** 個別オブジェクトの回転・スケール変形処理。

---

## 2. 状態管理（State）
キャンバスの表示状態を制御するために、以下のパラメータを保持する。

* `double scale` : 拡大率（初期値: `1.0`）
* `Offset offset` : スクリーン原点に対するキャンバス原点の移動量（Pan位置）

### 座標変換式
* **Canvas → Screen (描画時):**
    $$X_{screen} = (X_{canvas} \times scale) + offset.dx$$
* **Screen → Canvas (イベント検知時):**
    $$X_{canvas} = \frac{X_{screen} - offset.dx}{scale}$$

---

## 3. Flutterにおける実装戦略（アーキテクチャ）

パフォーマンスの最大化とレイアウトコストの削減のため、コンポーネント構造の動的拡張（SizedBox等のリサイズ）は行わず、**画面サイズ固定の `CustomPaint` 内でのアフィン変換（行列変換）**を採用する。

### コンポーネント構成（Widgetツリー）

```

[Stack] (画面全体)
├── [GestureDetector] (ピンチ・ドラッグ等のジェスチャー検知)
│     └── [CustomPaint] (サイズ：Size.infinite で固定)
│           └── [CustomPainter] (★ すべての描画・座標変換を担当)
├── [Positioned] (テキスト編集時のみ動的に重ねる通常の TextField)
└── [Align / Positioned] (画面に固定されるツールバーやインスペクタ等のUI)

```

### レンダリングパイプライン（CustomPainter内の描画順序）
`CustomPainter.paint` メソッド内で、描画の重ね合わせ（レイヤー構造）をコードの実行順で表現する。

1.  **最背面（スクリーン座標系）:**
    画面全体（ビューポート）を背景色（例: グレー）で塗りつぶす。
2.  **アフィン変換の適用:**
    `canvas.save()` の後、`canvas.translate(offset.dx, offset.dy)` および `canvas.scale(scale)` を実行。**これ以降の描画はすべて自動的にキャンバス座標系として扱われる。**
3.  **用紙エリア（キャンバス座標系）:**
    独立したメタ情報として定義された「用紙の境界（アートボード枠）」を、キャンバス座標 `(0, 0)` を起点として白色で描画する。（※オブジェクト群とは完全に分離された背景ガイドとして扱う）
4.  **オブジェクト群（キャンバス座標系）:**
    データモデルとして保持されているオブジェクト配列をループで回し、そのままのキャンバス座標で描画する。
5.  **変換のリセット:**
    `canvas.restore()` を実行し、スクリーン座標系に戻す。

---

## 4. 主要機能のロジック要件

* **ポインタ位置基準のズーム（Mouse Wheel / Pinch Zoom）**
    ズーム時にカーソル直下のキャンバス座標がズレないよう、新しい `scale` を適用した後に以下の式で `offset` を逆算して更新する。
    $$offset.dx = X_{screen} - (X_{canvas} \times scale_{new})$$
* **ビューポート・カリング（最適化）**
    描画パフォーマンス維持のため、現在のスクリーン領域（四角形）をキャンバス座標に逆変換し、その領域と交差しない（画面外にある）オブジェクトの描画処理をスキップするロジックを実装する。
* **用紙エリア（アートボード）の分離**
    用紙はオブジェクト配列には含めず、独立した環境設定として管理する。これにより、「誤選択の防止」「用紙エッジへのスナップ」「用紙枠基準での画像エクスポート」の処理をシンプルに保つ。

## 5. 技術選定の判定基準（Flame vs CustomPaint）
* ゲームエンジンの `Flutter Flame` は使用しない。最終的な描画エンジン（Impeller/Skia）は同じであり、 Flameを使用しても描画は高速化しない。
* 静的な図形やテキスト、接続線を扱い、かつFlutterネイティブのWidget（TextField等）との親和性を最優先するため、低消費電力で制御の柔軟性が高い `CustomPaint` が最適である。
